# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Expo version

This project is on **Expo SDK 54 / React Native 0.81 / React 19**. Expo's APIs change between major versions — read the exact versioned docs at https://docs.expo.dev/versions/v56.0.0/ before writing native/Expo code (per `AGENTS.md`).

## Commands

```bash
npm install            # install deps
npx expo start         # dev server; press i (iOS sim), a (Android), w (web), or scan QR in Expo Go
npx expo start -c      # same, clearing cache — required after changing .env vars
npm run ios            # native dev build on device/sim (needed for push; Expo Go can't do remote push)
npm run web            # web build (the static export Vercel serves)

# Regenerate the bundled court/class/pool data (scrapes live sources):
npm run build:data         # everything below, in order
npm run build:courts       # SF Rec & Parks indoor gyms
npm run build:sanbruno     # San Bruno RAC (Google Sheet)
npm run build:outdoor      # outdoor basketball/volleyball/tennis/pickleball/soccer/baseball + fitness courts (DataSF; greater-SF bounds — Camp Mather excluded)
npm run build:reservations # tennis/pickleball booked% (rec.us)
npm run build:directory    # court facility facts (sfrecpark directories)
npm run build:classes      # full ActiveNet catalog, 33 categories (+ Claude title translation if ANTHROPIC_API_KEY set)
npm run build:volunteer    # Rec & Park volunteer workparties (Salesforce Aura endpoint behind their calendar)
npm run build:pools        # swimming pools + schedules parsed from seasonal PDFs (pdfjs-dist)

# NYC (second city — see "Multi-city" below):
npm run build:nyc          # NYC outdoor courts/fields + amenities + sport attrs (NYC Open Data Socrata)
npm run build:nyc-indoor   # NYC rec-center indoor open-gym schedules (nycgovparks.org; Claude classifies ambiguous programs)
npm run build:nyc-classes  # NYC Parks free programs feed (+ PerfectMind openings, full descriptions, Claude title translation)
npm run build:nyc-reservations # NYC occupancy: citywide Parks permits + the 8 online tennis sites (also captures dusk + floodlight times)
npm run build:nyc-directory    # NYC Parks facility directories + official pickleball page + nycpickleball.com colour
npm run build:nyc-pools        # NYC's 79 free outdoor + 13 indoor rec-center pools (season-aware)

# Assistant service (optional, self-hosted — see "The assistant" below):
npm run export:chatbot     # app data → chatbot/data/*.json (re-run after any data refresh)
cd chatbot && .venv/bin/python -m uvicorn app:app --port 8000   # run it
cd chatbot && .venv/bin/python -m pytest -q                     # its 429 tests (CI does NOT run these)
```

`build:classes`, `build:volunteer`, `build:pools`, and the `build:nyc*` scripts need network access; `build:classes` / `build:volunteer` / `build:nyc-classes` optionally call the Anthropic API (Claude Haiku) to translate new class titles to zh/es when `ANTHROPIC_API_KEY` is set (cached in `scripts/*-i18n-cache.json`, degrades to English without a key), and `build:nyc-indoor` optionally uses it to classify ambiguous open-gym vs class programs (cached; excludes the ambiguous ones without a key). All build scripts share `scripts/lib/courts-common.js` (cache/slug/time helpers) and the live→cache→gate resilience pattern.

The JS app has **no test suite, linter, or typechecker** configured — it's plain JS (not TS). "Verifying" a change means running the app (`npx expo start`). There *is* a thin CI sanity gate: `npm run check` (`scripts/check-app.js`, run by `.github/workflows/ci.yml` on every push/PR) — every `.js` parses (esbuild/jsx), `lib/i18n.js` keeps en/zh/es at full key parity, and the generated `data/` modules load with non-trivial entry counts. Run it before committing; keep its data floors loose (they exist to catch gutted scrapes, not seasonal shrink). **`chatbot/` is the exception** — it has 429 pytest tests, and `npm run check` does not run them, so run them by hand when touching that directory.

## Architecture

A single-screen Expo/React Native app (also deployed to web as a static export) for finding places to play sports in SF and NYC. Five pieces fit together — the UI, the `lib/` feature stores, the generated `data/` pipeline, the multi-city seam, and an optional self-hosted assistant service:

### 1. UI — one big `App.js` + a bottom-tab shell

`index.js` → `Root` wraps `App` in `SafeAreaProvider` + `AuthProvider`, all inside `I18nProvider` (see i18n below). `App.js` (~1900 lines) holds the home map screen, all shared state, and the `CourtDetail` card. `BottomNav` switches four tabs via the `tab` state in `App.js`: `home` (map) · `classes` (`ClassesScreen`) · `social` (`SocialScreen`) · `profile`. Swimming pools are a **sport on the map**, not a tab — `lib/poolCourts.js` shapes the 9 pools into `swimming` court records and `components/PoolDetail.js` renders their schedule/fees in the `CourtDetail` card (see the sports paragraph below). Most other features render as **modals** (`AuthModal`, `RunModal`, `FriendsModal`, `FeedModal`, `SignalModal`, `SessionModal`, …) toggled from `App.js`. On first launch `App.js` shows `components/Onboarding.js` (a full-screen overlay: swipeable value-prop slides → pick interests → location primer → optional account nudge) — gated on the `recreate.onboarded.v1` AsyncStorage flag; returning users skip it and get the immediate location request as before. A **one-time coach mark** (persisted under `recreate.coach.sportfab.v1`, mirroring the loc-banner pattern) then points at the sport FAB on the map, dismissed by tapping it or opening the sport dial. The location prompt fires in context from the location slide (`onEnableLocation`); "Create account" opens `AuthModal` inline in signup mode (its `initialMode` prop), and finishing onboarding — or a successful signup, detected via the auth-state transition — dismisses the overlay onto the map underneath. `finishOnboarding` persists the interest picks. Interest picks are stored on-device via `lib/interests.js` (`loadLocalInterests`/`saveLocalInterests`, key `recreate.interests.v1`) so recommendations personalize even signed-out; `App.js` computes "effective" interests (the signed-in profile's `favorite_sports`/`favorite_categories` if set, else the local picks) and passes them to `SocialScreen` → `RecommendPane`. Long lists (Classes, activity feed) share `components/ScrollTopFab.js` (`useScrollTop` hook + FAB): a back-to-top arrow that appears on swipe-up-while-scrolled. The Classes tab also has a scroll-linked collapsing header (title/subtitle/info block fades as one unit, then its height collapses, driven off scroll offset for smoothness).

The map is **Leaflet + OpenStreetMap inside a WebView** (no API key/billing). `components/CourtMap.js` is the native (WebView) implementation; `components/CourtMap.web.js` is the web variant — Metro picks `.web.js` automatically on web, so **keep marker/animation/clustering logic in sync across both files**. Markers are **grid-clustered by screen distance** below `DECLUSTER_ZOOM` (nearby courts collapse into a count bubble — orange if any is open now, grey if none; tap to fit-bounds in), re-clustering on `zoomend` only; past that zoom every court renders individually. Open courts draw as the full sport glyph, **closed/no-drop-in courts recede to a small faded dot** (an open/closed hierarchy). Per-sport glyphs are inline SVG; **pickleball has no emoji, so `components/SportGlyph.js` renders a drawn/rasterized lime perforated ball** (`assets/pickleball.png`) for the sport dial while the map markers draw the same ball as SVG.

### 2. `lib/` — feature stores, each with the same Supabase-or-local pattern

`lib/supabase.js` exports a `supabase` client **or `null`** when `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` are unset. This null-check is the core architectural seam: **every social/shared feature must degrade gracefully when `supabase` is null** — crowd check-ins fall back to on-device `AsyncStorage`, and account/social features hide entirely. Don't assume the client exists.

Each file in `lib/` owns one feature's data access (e.g. `crowd.js`, `reviews.js`, `runs.js`, `signals.js`, `friends.js`, `feed.js`, `chat.js`, `push.js`, `playerCheckins.js`, `favorites.js`, `blocks.js`, `reports.js`). **Trust & safety (App Store UGC requirement):** `lib/blocks.js` (`getBlockedIds` — in-memory-cached, invalidated on block/unblock) is filtered into every social loader (`signals`, `chat`, `feed`, `friends`) so a blocked user's content disappears app-wide; `lib/reports.js` files content reports. Report/block surface on chat messages (long-press) and reviews (report-only — reviews have no `user_id`); Settings has a Blocked-users manager, and account creation requires agreeing to the EULA/privacy terms. Beyond UGC, `content_reports` also carries **data-quality + problem reports** (migration `023`, folded into `schema/10_moderation.sql`): `kind 'data'` is the one-tap "looks wrong? report it" flag on the court card's schedule, `ClassDetail`, and the pool card's expanded view (shared `confirmReportData()` flow; `ref_id` names the entity — `court:<id>:<sport>` | `class:<id>` | `pool:<id>`), and `kind 'issue'` is Settings' free-text "Report a problem" dialog (text in `reason`, ≤500 chars). Both require sign-in like all reports and are reviewed out-of-band in the Supabase dashboard. **Posting a review requires sign-in when reviews are shared** (Supabase configured): `CourtDetail` shows a "Sign in to write a review" prompt (routing to the Profile tab via `onNeedSignIn`) and RLS enforces it (`reviews` insert policy is `to authenticated` + `auth.uid()` — migration `016`, folded into `schema/02_reviews.sql`); local-only reviews stay open, and the report flow is unchanged. Settings also links the **Privacy Policy / Terms (EULA) / Support** pages; the App Store privacy nutrition label is reconciled against the policy in `docs/privacy-nutrition-label.md`, and the same collected data types are declared in `app.json` → `ios.privacyManifests` (Location omitted — on-device only). **Accessibility:** every icon-only control (sport/filter FABs, recenter, ✕ close buttons, loc-banner dismiss, bottom-nav tabs, review Report) carries an `accessibilityLabel`/`accessibilityRole` (a11y strings under `a11y.*` in i18n). Realtime features merge incoming rows **incrementally by `id`** (e.g. `mergeCheckIn`) rather than refetching. `lib/auth.js` is the `AuthProvider` context (session + profile). `lib/useCourts.js` is the launch-time data loader. `lib/hours.js` holds the open-now / open-gym schedule logic shared between the map filter, Nearby list, and run/signal time pickers. `lib/recommend.js` (`buildRecommendations`) builds the Social tab's auto-revolving **"Recommended for you"** pane (`components/RecommendPane.js`) from bundled data — open-gym games for the user's `favorite_sports` and rec-center classes with openings in their `favorite_categories` (class-category interests, both edited on the profile). Recommendations are **tiered**: (1) if any interests are set, filter to them; (2) else fall back to the user's **check-in history** (`lib/playerCheckins.js` `loadMyStats` → the sports they've logged, surfacing their most-visited court first — `RecommendPane` fetches this when interests are empty and passes it as `history`); (3) else, with neither interests nor history (signed-out or brand-new), recommend **nearby** (any sport/class, closest first). Tapping a game rec opens that court's `CourtDetail` **on the rec's sport** (the tap threads the sport through `onPickCourt(id, sport)`, switching the map's sport so e.g. a ping-pong rec doesn't open on basketball); tapping a class rec — or any card on the Classes tab — opens `components/ClassDetail.js`, a bottom sheet with the class's schedule / location / cost / ages / availability / description (the catalog blurb, or "No description available") + Directions and a Register-on-ActiveNet link. Free walk-in drop-ins that can't be registered online (ActiveNet shows a "View Registration Info" fee placeholder) are flagged `noOnlineReg`, priced **Free**, and get a "just show up at the start time" notice. ActiveNet **delists** cancelled/ended classes, so a re-scrape drops them automatically; on native, `ClassesScreen` also hides any bundled class missing from a healthy live-catalog fetch (`lib/classesLive.js`) so a between-scrape cancellation disappears in real time. **ActiveNet scrape gotchas** (`scripts/build-classes.js`): query **one category id per request** — the multi-id search repeats some categories' items across pages and silently omits others (`lib/classesLive.js` `GROUPS` must stay in sync with the build's id list, or the delist-hiding wrongly hides whole categories on native); drop-in series arrive as one activity **per date** and are collapsed into a single card keyed by the **latest** instance's id (earlier instances delist while the series still runs); drop-ins for map-tracked sports are skipped (`MAP_SPORT_DROPIN_RE`) since their hours are the map's open-gym blocks; "View Fee Details" placeholder fees get real prices from `rest/activity/detail/estimateprice/<id>`. `ClassDetail`'s sheet pins Directions/Register **outside** its ScrollView; making the ScrollView actually scroll on device took TWO gotchas (both invisible on web): (1) the sheet's maxHeight must be a **static numeric value in `StyleSheet.create`** (`Dimensions.get('window').height * 0.85`) — a *percent* maxHeight is ignored when sizing children by native Yoga, and an *inline/style-array* numeric maxHeight also failed to constrain on device; only the static registered form (the same pattern as `CourtDetail`'s card) lets the `flexShrink: 1` ScrollView shrink and scroll. (2) The tap-to-close backdrop must be an **absoluteFill Pressable stacked BEHIND the sheet as a sibling**, never a Pressable *wrapping* the sheet — a Pressable ancestor swallows the ScrollView's pan gesture on device, freezing scroll (touches on the sheet bubble up the sheet's own branch and never reach the sibling, so no empty-`onPress` guard is needed). Apply both patterns to any new bottom sheet with scrollable content. The same recommendations feed **interest-based local notifications** (`lib/localNotify.js`, called from `App.js` on launch + foreground): on-device reminders ~30 min before today's matching games/classes, deduped per day in `AsyncStorage`, gated on having interests + notification permission. Server push (while the app is closed) is handled entirely in Postgres: `supabase/schema/07_push.sql` triggers call Expo's push API via `pg_net` (`send_push()`) when a friend posts a signal, plans a run, logs a check-in, or reports a court's crowd level — plus direct pings (someone joined your run/signal, a session got confirmed, a friend request was accepted). The four **broadcast** notifications (check-in, crowd vote, signal, run) are gated on a per-row `notify` flag the client sets from the user's `profiles.share_activity` setting (Settings → "Share activity with friends", default on); when that setting is off, the client prompts per-action (`lib/activityShare.js` `resolveNotify`) so a private user can still share one thing. `send_push()` and `accepted_friend_ids()` are `SECURITY DEFINER` and **revoked from anon/authenticated** (only the trigger functions, running as owner, may call them) — otherwise a client could push spam or enumerate friend lists. `send_push()` sends **one request per token** (migration `013`): Expo 400s a whole request that mixes tokens from different projects/experience IDs, so batching let one stale token silence a broadcast — a real gotcha after re-creating the EAS project left a device with both an old-`hoopmap` and new-`recreate` token. Crowd check-ins are keyed **court + sport** (`check_ins.sport`, migration `024`, folded into `schema/01_crowd_check_ins.sql`): a pin is a whole facility — Miraloma Playground carries a gym, tennis courts and a ball diamond — so a court-only key made "packed" at the hoops mark the diamond packed too, on the marker, the card and the push. `lib/crowd.js` keys every history by `crowdKey(courtId, sport)` and `historyFor()` reads one sport's; rows predating the change carry a null sport, stay under the bare court id, and are merged into every sport until they age out of the 24h window (that fallback is deletable once none can remain). Crowd-update pushes are **rate-limited to one per voter+court+sport per 10 min** via `crowd_notify_log` (migrations `014`, `024`) — rapid level switches (each an insert + delete) would otherwise push to friends on every tap, while keying the cooldown on the court alone would swallow "gym packed, tennis empty" as one report. `lib/favorites.js` (`useFavorites` hook) stores favorites on-device via `AsyncStorage` (works fully signed-out, like crowd check-ins) as a **court id → sport** map: a court is favorited *for the sport you were viewing* when you starred it. The sport speed-dial's ⭐ **Favorites** entry switches the map into a personal view of just those courts, each marker/card judged open **for its favorited sport**; the card's star (`toggle(id, sport)`) saves/removes the court for the displayed sport. `lib/sports.js` defines the tracked **playable** sports (`SPORTS`: basketball, volleyball, ping pong, badminton, pickleball, tennis, **soccer**, **baseball**, **swimming** — soccer & baseball are outdoor-only field sports, swimming is the public pools (see below). SF fields are strictly designated by DataSF type: soccer = `Soccer Field` + `Multi-Use Turf`, baseball = `Ball Field` (diamonds). A single field is never both; a park with a separate pitch & diamond unions both onto one pin, exactly like a park with both a basketball & tennis court) plus the `ANY_SPORT` (`'any'`) sentinel — "just down for rec", a sport-less **"down to play"** signal (no real schedules key off it, so the session sheet falls back to a default sport for court/time suggestions). It also exports `WEIGHT_ROOM` (`'weightroom'`), `GOLF` (`'golf'`), `MAP_SPORTS` (`SPORTS` + both, for the map dial), and `PLAN_SPORTS` (`SPORTS` + both, for the social composers): weight room and golf are **facility views**, not sports — the weight room is scraped into `dropins.weightroom` like a sport, and the 6 SFRPD golf courses are hand-curated in `data/manual-courts.js` with daylight-hours `dropins.golf` weeks plus a per-course `golf` block (holes/par/yardage, a short course description, curated green fees like the pool `FEES` tables — bump ~annually — and tee-time booking + official-website URLs) that `CourtDetail` renders; golf-only filter chips (9/18 holes, beginner, driving range) ride the generic `AMENITIES` machinery, self-hiding outside the golf view because only golf entries carry `c.golf`. Both views are selectable in the map's sport speed-dial (`MAP_SPORTS`), so all the generic marker/open-now/card machinery works. **Swimming**, by contrast, is a *full* playable sport (in `SPORTS`, so favoritable/plannable/down-to-play): `lib/poolCourts.js` turns the 9 pools (`data/pools.js`) into `swimming` court records whose open-now comes from a `dropins.swimming` week built from the pools' **public-swim** sessions (lap/family/senior/water-exercise/parent-tot; lessons/camps/rentals excluded), and `components/PoolDetail.js` renders the `pool` block (full weekly schedule by session kind, warm/cool groups for North Beach, collapsible fees, PDF) in the `CourtDetail` card. Session-type filter chips (Lap/Rec-Family/Senior/Lessons/Water-exercise) ride the same `AMENITIES` machinery, keyed off `c.pool.programs` and self-hiding outside the Swimming view. (Pools were a separate tab before; `PoolsScreen` was removed.) The weight room and golf, by contrast, are kept out of `SPORTS` — so **favorites/profile** never treat them as sports, and `isPlayableSport(id)` guards the map→`SocialScreen` hand-off (`App.js` coerces a facility-view map sport back to `DEFAULT_SPORT`) — **but both social composers can plan/signal a lifting session or a round** via `PLAN_SPORTS` (Plan a session in `RunModal`, "I'm down" in `SignalModal`). Only Mission, Minnie & Lovie Ward, and Glen Park currently publish weight-room drop-in hours; the weight-room view also includes the 12 DataSF **outdoor fitness courts** (`Adult Fitness Court/Course`, mapped to `dropins.weightroom` by `build-outdoor-courts.js`). Both planned runs and signals carry a `sport`; a run's/signal's sport scopes its court/time suggestions, and signals may be `ANY_SPORT`. **Plan a session (`RunModal`) is for any planned session, not just casual pickup** — it offers an Indoor/Outdoor/Either filter over the court list for sports that have both (the map's `PLACE_OPTS`), and requires a concrete court + time. **A "down to play" signal (`SignalModal`) can optionally seed location up front**: an indoor/outdoor `place` and/or a preferred court (`rec_signals.place` + `pref_court_id`, both nullable — blank = "let friends decide", added in migration `015`), surfaced on the session sheet as a "Prefers: …" line. When responding to a signal, a participant suggests an **activity → place → time** (`rec_signal_participants.proposed_sport` + `proposed_court_id` + `proposed_at`); the host confirming a suggestion promotes its sport onto the signal (so an `ANY_SPORT` signal becomes concrete). Joining a run or signal makes you a member of its `chat_messages` group thread (`lib/chat.js`) — `chat_messages` holds run/signal group chats and 1:1 direct chats in one RLS-scoped table; joining a signal from the session sheet also posts an announcement into that chat.

**i18n (`lib/i18n.js`):** the app is fully localized to English / 中文 / Español. `I18nProvider` holds the chosen language (persisted in `AsyncStorage` under `recreate.lang`); React components read `const { t, lang } = useI18n()`. Plain non-React modules (`datetime`, `crowd`, `hours`, the `lib/*` error messages) translate through the module-level `tg(key, vars)` helper, which mirrors the current language into a global so it works without context. All strings live in one `STRINGS` dict keyed by language — **keep en/zh/es at full key parity** (a quick `eval`-based count check catches drift). Composed sentences use `{placeholder}` interpolation, not string concatenation. External data (court/pool names, addresses, scraped class/schedule text) stays in its source language; scraped **class titles** are the exception — they're pre-translated at build time (see `build:classes`).

Supabase DDL lives in `supabase/schema/` (canonical, numbered 01→10 — `09_account_deletion.sql` is the SECURITY DEFINER `delete_account()` RPC behind Settings → Delete account; `10_moderation.sql` is trust & safety: `blocked_users` + `content_reports` — **run in order** on a fresh DB, later domains depend on earlier) and `supabase/migrations/` (deltas for existing DBs — see the table in `supabase/README.md` for the current latest). When adding a feature with a new table, add a numbered schema file and document its dependency order in `supabase/README.md`.

### 3. `data/` + `scripts/` — a generated, self-refreshing data pipeline

**`data/courts.js`, `data/courts.json`, `data/outdoor-courts.js`, `data/classes.js`, `data/pools.js`, etc. are GENERATED — never edit them by hand.** Each is produced by the matching `scripts/build-*.js`, which scrapes a live source (sfrecpark.org via cheerio, DataSF `ib5c-xgwu`, rec.us API, a Google Sheet, ActiveNet). The two hand-authored data files are `data/manual-courts.js` (fully-static courts merged in at runtime by `lib/useCourts.js`, deduped by `id` — this is where the 6 golf courses live) and the `CENTERS` table inside `scripts/build-indoor-courts.js`. A third hand-written file, **`data/sf-classes.js`**, is SF's program *aggregator* (the SF analogue of `data/cities/index.js`): it merges `data/classes.js` (ActiveNet) with `data/volunteer.js` into the one catalog every consumer reads — `ClassesScreen`, `RecommendPane`, `postbuild-web.js`, `export-chatbot-data.js`. Merging there rather than inside either generated file keeps each build owning exactly one output, so a failed volunteer scrape can never blank the class catalog.

**Volunteer opportunities (`scripts/build-sf-volunteer.js` → `data/volunteer.js`)** are the second half of SF's Classes tab, and the source is unlike any other. SFRPD's volunteer calendar renders **nothing** server-side — the page is a 3 KB Visualforce shell that boots a Lightning Out component, so there is no HTML to parse. The data comes from a public Apex controller (`SFRPCalendar`) behind Salesforce's **Aura endpoint** (`POST /aura`, `getFilterJobs`), which needs no auth and answers even with a junk `fwuid`, so there's no framework nonce to scrape first. **Only ever call its READ methods** — the same controller exposes `insertVoulnteerInfor` (sic), the signup write path. Two shape gotchas: the feed is an **archive, not a calendar** (~87% of its ~1,700 rows are shifts that already happened, back to 2020) and each recurring workparty emits **one row per date**, padded with placeholder instances as far out as 2030 that add no jobs the next 90 days don't already have — so the build keeps upcoming shifts inside a 180-day horizon and collapses them to one card per job, exactly like `build-classes.js` does with ActiveNet drop-in series. ~1,700 rows → **~36 entries**, a number that drifts week to week as workparties are scheduled and age out. They file under the `philanthropy` category (the chip the app labels **"Volunteer"**) with a secondary `nature`/`social` tag, and carry **`source: 'sfrpd-volunteer'`** — which is load-bearing in two places: `ClassesScreen`'s ActiveNet delist check must skip them (they are not in ActiveNet, so delisting would hide **every one** on native, and counting them would drag its 80% health ratio down), and `ClassDetail` swaps the "Register on ActiveNet" CTA/footnote for the volunteer calendar (sending someone to ActiveNet for a workparty is a dead end) and shows the partner org as **Hosted by**, not Instructor. Their `spots` is a real per-session "volunteers still needed", so it is shown exactly rather than collapsed to "lots of spots" — that collapse now applies only to source-less ActiveNet rows, whose count is a whole term's seat pool. Park coords come from the bundled court data plus a curated `MANUAL_COORDS` table, because the feed carries a street address but no lat/lng and uses internal park names (`GGP Sec 2 Rhododendron Dell`) the public court data has no row for; coordinates are the **work site**, not the park centroid, since Golden Gate Park spans three miles. No per-job deep link exists (the page reads a job id into `vJobId`, but no obvious query param binds to it), so every entry links to the calendar itself.

Build resilience pattern (shared by every script): each source falls back **live → cache → curated**, with a `scripts/*-cache.json` last-good snapshot and a validation gate that aborts the build (keeping old data) if too few records scrape — so an upstream site redesign fails loudly instead of publishing empty data.

**Pools are the unusual one (`scripts/build-pools.js` → `data/pools.js`):** the 9 SF public pools post their weekly swim schedules only as *seasonal PDFs* (re-issued every few months) on their facility pages. The script discovers each pool's current schedule PDF link live, downloads it, extracts positioned text via `pdfjs-dist` (a build-only devDep — not bundled into the app), and reconstructs the weekly grid geometrically (merge text fragments → map cells to day columns by x → pair each activity label with the time below it → classify into a session `kind`). Output is `sessions[dow] = [{ kind, start, end }]` (0=Sun..6=Sat, minutes-from-midnight, same convention as court schedules), plus the city-wide `POOL_FEES` and `POOL_CLOSURES`. A facility posting separate warm-/cool-pool PDFs (North Beach) gets each session tagged `pool: "warm" | "cool"` by source PDF — the tag is part of the cross-PDF dedupe key (both pools can run the same activity at the same time) and `components/PoolDetail.js` renders the groups under ♨️/❄️ headers. Pool coordinates/addresses/phones and the `season`/closure labels are **curated** in the script's `META`/`FEES`/`CLOSURES` tables (pages have no lat/lng; fees change ~annually, not seasonally) — bump these by hand each season. `PoolDetail` renders a localized label per `kind` and links out to the official PDF as the source of truth. Each pool also gets a `desc` scraped from its facility page's own blurb (`pageDesc` — first substantial paragraph surviving the `DESC_SKIP` boilerplate filter; 3 of 9 pages have none, which is fine), shown in the pool card.

**The court directory (`scripts/build-court-directory.js` → `data/court-directory.js`)** layers three sources, in trust order. (1) **SFRP is canonical**: the sfrecpark tennis/pickleball directory tables, plus each pickleball court's **posted schedule PDF** (linked from "See schedule" cells) parsed via `pdfjs-dist` into tagged block weeks — `playWeek` (authoritative posted hours that **replace** `court.dropins[sport]` at runtime in `lib/useCourts.js`, so open-now/markers/schedule agree — honest gaps included) or `openPlayWeek` (an overlay `getDropinWeek` carves into the base hours with interval subtraction so times never overlap). Some posters are **flattened images with no text layer** (Presidio Wall, Rossi as of 2026-07) — those use hand-transcribed `PDF_FALLBACK` entries, and Moscone (which parses live) has a transcribed fallback as insurance; the build logs every fallback with the poster URL — **re-verify the transcriptions whenever SFRP posts a new poster**. Court-split nuance the weeks can't carry lives in curated `OPEN_PLAY_NOTES`/`TENNIS_ADJUST` tables. (2) **Community sources are advisory color, never schedule truth**: pickleballsf.com venue descriptions (`pbsfEnrich` — schedule-looking text there is only *logged* as a cross-reference), tennissf.com hitting-wall flags (`tennisWalls`) and per-court player ratings (`tsfRatings` — overall/surface/crowded + matches played, from their `court_detail` pages). **Their content is credited on the card and must stay that way**: the descriptions are pickleballsf's own writing, and the card renders it, so `App.js`'s `SourceCredit` prints "via pickleballsf.com" / "via tennissf.com" beneath it, linking to the exact venue page. The build carries that provenance — `descSrc` from the WordPress post's canonical `link`, `tsf.src` from the `court_detail` slug — and **both pickleballsf paths must set it** (outdoor venues and the separate indoor rec-center pass assign `desc` independently; only patching one leaves credits pointing at the site root). Slugs don't track court names (Larsen is `larsen-playground-pb-court-hub`), so never construct these URLs — take the canonical one the API returns. Facts alone (court counts, wall flags) don't need this; reproduced prose does. pickleballsf is read through its **WordPress REST API** (`wp/v2/posts`, browser UA required — mod_security 406s otherwise; venue pages are posts, and their two-column Enfold layout means scoping to `.flex_column.av_two_third` drops the sidebar nav), which also yields each page's `modified` date — the only staleness signal the source has, and load-bearing: pages last edited in 2022 were shipping "not on Spotery" (SFRP's pre-rec.us system) onto live cards, so `pbsfFreshen` drops dead-booking-system sentences at any age and strips recency claims ("New", "recently resurfaced") past two years. **The one narrow exception to "never schedule truth" is `communityWeek`**: SFRP lists "Pickleball (Indoor)" as an amenity at Hamilton, Minnie & Lovie Ward and Upper Noe but publishes no drop-in row, and `build-classes.js` skips map-sport drop-ins, so those sessions were invisible app-wide. `lib/useCourts.js` merges a `communityWeek` into a sport **only when that sport's week is empty**, so it is structurally incapable of overriding SFRP; blocks are tagged `'community'` and the card prints `court.communityHours` naming the source. Trust it only that far — measured against the 8 sessions where SFRP also publishes, pickleballsf got the **day 8/8 and the start time 7/8, but the end time only 3/8** (off by −90 to +60 min, i.e. wrong in *both* directions). A schedule the page itself captions with an old year is rejected outright (Upper Noe's says "(2022)"), and it stays in the map so it self-heals if they ever refresh the page. The same indoor pass also lifts **`loaner`** (`'paddles'` | `'paddles-balls'`, from the page's own prose) — five of the six gyms lend gear, no official feed records it, and "can I turn up with nothing?" is the question a beginner actually has; it drives the self-hiding `amenity.loaner` chip. Facts and schedule are gated **separately** (`PBSF_INDOOR`'s `schedule` flag): the three gyms whose hours SFRP does publish take facts only, because emitting a `communityWeek` there would be discarded at runtime but would still light the "times reported by…" warning over city-sourced hours. Court counts are deliberately **not** taken from this source — `total` stays SFRP-only so the card's count chip never mixes trust tiers. (3) A court can have a **wall-only minimal entry** with no SFRP directory row (Sunset Rec Center) — the card gates its count chip on `!!dir.total`. **Name-matching must not be hard-gated on DataSF**: `matchCourt` prefers courts already known to offer the sport (it disambiguates overlapping park names) but falls back to the full list, because a court's `sports` come from DataSF while SFRP's directory is the better authority on what a facility actually runs — gating on DataSF silently discarded SFRP's own pickleball rows for Alta Plaza, States Street, Willie "Woo Woo" Wong and Goldman. When a directory row counts **walk-up** courts for a sport the court has no hours for, `lib/useCourts.js` gives it the park's daylight `schedule`, the same hours every other outdoor pickleball pin runs on. It is gated on `walkup > 0`, not `total > 0`: Goldman has 5 pickleball courts but zero walk-up — reservation-only, fee-charging, third-party-run on its own 8AM–10PM day — so park hours would overstate it by five hours daily, and it keeps its facts but stays off the map until it has real hours. Indoor gyms are excluded outright (building hours are not open-gym hours).

`lib/useCourts.js` loads data **bundled (instant) → cached → remote** (`EXPO_PUBLIC_COURTS_URL`) so the app renders offline immediately then revalidates. It also merges the auxiliary generated maps onto each court: `reserved` (booked%), `directory` (facility facts + the playWeek replacement above).

### 4. Multi-city (SF + NYC)

The app now covers **two metros: San Francisco and New York City**, with an architecture built to add more. Key pieces:

- **`lib/cities.js`** — the city registry: each city is `{ id, name, center, zoom, tz, bbox, features:{classes,pools,reservations,directory,golf}, subregions? }`. Note the reservation UI is **not** gated on `features.reservations` — it keys off a court actually carrying `reserved`, which is why NYC occupancy lit up the existing card/list/composer surfaces without a new render path. `nearestCity(lat,lng)` auto-detects from a location fix; `getCity(id)` resolves the active one; `recordSubregion(r)` + `inSubregions(r, selected)` power the borough filter. **Every court/class record carries a `city` field**; consumers default `(c.city || 'sf')` so older cached payloads still work — SF ids are **byte-identical to before** (Supabase rows + on-device favorites key off them; never change SF `slug()` output).
- **`App.js`** holds `activeCity` (persisted `recreate.city.v1`, auto-detected on first fix unless manually chosen) and per-city borough selection (`recreate.subregions.v1`). It filters the merged court list (`cityCourtData`) and class catalog by city + subregions, hides SF-only tabs/sections via the city's `features` flags, and threads the city center/zoom into `CourtMap` (which **remounts on tab switches**, so its initial view must come from the active city). The **Settings** sheet (in `AuthModal`→`SettingsScreen`) has the City picker and, for cities with `subregions`, an "Areas" multi-select (NYC boroughs).
- **Per-city data lives in `data/cities/<id>/`** (`outdoor-courts.js`, `indoor-courts.js`, `classes.js`, `reservations.js`, `directory.js`, `pools.js`), aggregated by the hand-written **`data/cities/index.js`** (static imports for Metro; exports `CITY_COURTS` + `CITY_CLASSES` + `CITY_RESERVATIONS`). That aggregator is **not a re-export** — it is where per-city quirks become uniform records so nothing downstream learns them: it expands the compact `sports` array to `{schedule,dropins}`, applies NYC's per-weekday dusk close and per-sport floodlight extensions, expands run-length-encoded occupancy back to slot maps, and unions in sports the official directory adds. `lib/useCourts.js` folds `CITY_COURTS` into `EXTRA_COURTS` and `CITY_RESERVATIONS` into the `reserved` lookup. NYC is **bundled-only** (no remote-refresh URL); the crons commit it.
- **NYC builders** (`scripts/cities/nyc.js` config + `scripts/lib/socrata-outdoor.js` generic adapter, run via `scripts/build-city-outdoor.js`): outdoor courts from NYC Open Data Socrata (`qnem-b8re` Athletic Facilities joined to `enfh-gkve` Parks Properties). The adapter is **config-driven** — `sportFlags` (boolean col→sport), `factFields` (lighting/accessible/surface), `amenities` (key-join by gispropnum → `water`/`restrooms`), `reservable` (tennis permit system → `facts[sport].reservable` + court `booking`), and `sportAttrs` (per-sport attributes from boolean cols or a text-field regex → basketball full/half court from `dimensions`, soccer regulation pitch, baseball adult diamond). Surfaces are normalized at filter time (`surfaceCats` in `App.js`). `scripts/build-nyc-indoor.js` scrapes nycgovparks rec-center weekly schedules (open-gym vs class via rules + description + Claude fallback; **WAF challenge-blocks bursts — concurrency ≤2, paced**). `scripts/build-nyc-classes.js` parses the nycgovparks events RSS feed (the Socrata events dataset is dead) + enriches from PerfectMind (real openings, ages, deadline, full descriptions) and other reg pages (anchored full-description extraction); classes carry a **primary category + secondary `tags`** (multi-tag) incl. `nature`/`learn`/`film` categories and `philanthropy`/`accessible`/`performances`/borough themes.
- **NYC occupancy** (`scripts/build-nyc-reservations.js` → `data/cities/nyc/reservations.js`) is NYC's rec.us analogue, and it merges into the **same `reserved` contract** SF uses, so `lib/reservations.js` and the whole card/NearbyList/RunModal render path serve both. Two unrelated sources, distinguished by `kind`: **`'permit'`** — NYC Parks issues season permits to leagues, so the court is simply *taken* and you cannot book it, from the undocumented JSON API behind the permit map (`/api/athletic-fields?datetime=…` returns `{dusk, l:[system ids unavailable]}` for the **whole city in one request**, so a 30-min sweep of 7 days is ~217 requests total); and **`'reserve'`** — the 8 tennis sites taking $15/hr bookings via `/tennisreservation/availability/<id>` HTML grids. The permit join is exact and needs no name/distance matching: the API's `system` id is a column in the same `qnem-b8re` dataset the outdoor build scrapes, next to `gispropnum`, which `socrata-outdoor.js` now emits on every pin as **`key`** — never parse the sport out of the system id string, read it from the row's sport flags. Payload is **run-length encoded** (`runs: [[startIdx, endIdx, taken]]` on a 30-min grid from `ORIGIN`) and expanded back to slot maps by `data/cities/index.js`: permits are contiguous by nature, so this is ~5.3k runs / ~157 KB instead of 37.8k slot keys / 921 KB. Index math uses `Date.UTC` on the literal wall-clock fields in **both** the builder and the expander — parsing them as instants would shift every index across a DST boundary and vary by build host. Permit coverage is **sparse**, so entries carry `window`: inside it a missing key is a genuine zero, outside it is no data. Denominators are load-bearing (see `lib/reservations.js`): **both** halves count against the GIS court count for the park, so a reading can't contradict the court-count chip beside it, and 2 booked courts at Riverside read "2 of 20 · 16 walk-up" rather than "fully booked" (see the overlap warning below for the trap here). The two halves fall back to cache **independently** — an unrelated tennis hiccup must not discard a good citywide sweep, or silently republish week-old permits. Permits get their own vocabulary in the UI (`court.permitted*` keys, `{src}` names the source): a permitted court is *held*, never "booked", and telling someone to go reserve it would be wrong. Refreshed **daily** (`refresh-nyc-reservations.yml`) — permits barely move hour to hour, but the 7-day window has to roll forward or its far end goes dark.
- **NYC pools (92) ride the same `swimming` sport as SF's 9** — `scripts/build-nyc-pools.js` → `data/cities/nyc/pools.js` in the identical POOLS record shape, so `lib/poolCourts.js` (now city-agnostic; it maps SF **and** NYC) and `components/PoolDetail.js` render both with no new path. Far simpler than SF's PDF geometry: **outdoor** (79) share ONE citywide schedule stated in prose — 11 a.m.–7 p.m. daily with a **3–4 p.m. cleaning break**, so two blocks a day, free, no membership; **indoor** (13) have a real per-facility weekly grid in the `#Pool-schedule` table of the rec center's schedule page — the *second* `table.schedule-table` on the page, which is why `build-nyc-indoor.js` (it matches only the first) never saw it. **Fees now travel on the pool record**, defaulting to SF's `POOL_FEES`: `PoolDetail` used to import SF's table directly, which would have priced NYC's free outdoor pools at SF rates. **Season is read, not hardcoded**: NYC publishes no machine-readable start date, only a live banner, so the build ships what the site says *now* (`SEASON.checked` dates the claim) and out of season the outdoor pools carry **no sessions at all** rather than advertising swim hours in February. An indoor pool with an empty grid is real data, not a parse failure — 6 of 13 are closed for reconstruction, mechanical failure or summer lifeguard reassignment — so the build lifts the page's own alert into `notice` ("closed for reconstruction") and the card shows that instead of a blank week. Note `/nyc/pools` does **not** exist yet: the pool landing pages are still an SF-hardcoded family, unlike the city-driven sport pages.
- **Handball is a full playable sport, and it exists for NYC only.** 1,853 active facilities — more than basketball's 1,435 — across 484 park pins; one-wall handball is near-unknown outside the northeast, so SF has none, and the filters/pages self-hide accordingly (there is no `/handball`, only `/nyc/handball`). Adding it was the documented one-line-per-place path: `lib/sports.js`, an emoji entry in **both** `CourtMap.js` and `CourtMap.web.js`, `sportFlags` in `scripts/cities/nyc.js`, `ORDER`/`ALL_SPORTS` in the script helpers, and `sport.handball` in en/zh/es.
- **`scripts/build-nyc-directory.js` → `data/cities/nyc/directory.js`** carries the qualitative facts NYC's GIS data lacks, from NYC Parks' own `bigapps` feeds (`Prop_ID` **is** `gispropnum`, so the join is exact — 90–97% land on a pin). It ships tennis **surface** (real "Clay"/"Fast Dry"/"Har-Tru", where Socrata says "Asphalt"), **phone**, and NYC Parks' prose **`info`** (bubble seasons, lessons, which courts a permit covers). It deliberately ships **no court counts**: the directory and the GIS dataset disagree on ~20% of parks (tennis 51/64 agree, handball 366/452, basketball 86/122) and neither is clearly right, so **GIS stays canonical** and the build only logs the differences. Only `Indoor_Outdoor='Outdoor'` rows merge — several parks have an indoor bubble under the same `Prop_ID`, and its clay surface doesn't describe the outdoor courts. It merges into **`facts[sport]`, not `directory`**: that slot is SF-shaped and `App.js` hides the entire NYC facts row when it's present, so using it would trade these facts away for the chips already there.
- **Pickleball is the one sport where NYC's GIS layer is badly wrong, and the fix is an official page, not the community one.** Pickleball is lined onto existing tennis and handball slabs, so `qnem-b8re` records those courts under the original sport and never re-flags them: GIS knew 11 pins where NYC Parks' own `/facilities/pickleball` lists **24 locations / 72 courts**. Because that page *is* official, its entries carry `add: true` and `data/cities/index.js` unions them into the pin's sports — the only place a directory pass may add a sport — so those courts get hours, markers, filters and permit occupancy like any other. NYC pickleball went 11 → 24 pins. One location (Francis Lewis Park) has no GIS athletic facility at all and is logged rather than invented.
- **`nycpickleball.com` is advisory colour and may never add anything** — the NYC counterpart to `pbsfEnrich`, same trust tier. It ships `nets` (provided vs **BYON** — decisive when the courts are lines on a tennis slab), `openPlay` (players' own words) and `community` (the Slack channel / TeamReach code that organizes the venue), attached **only** where the official page or GIS already establishes pickleball. Its times **never** reach `dropins` and render attributed ("Players report: …") — organized open play is players agreeing to show up, not posted hours, and showing it as hours would send someone to an empty court on the city's authority. Venues it lists that no official source does (Roosevelt Island, Pier 2, school yards) are **logged, not published**. Parsing gotchas worth keeping: match the group code on **cleaned** text (`<strong>TeamReach code</strong>: X` puts a tag between "code" and its colon), take the Slack channel from the anchor that points at their Slack (a bare `#…` scan over raw HTML picks up Squarespace **block ids** — that once shipped `#block-d512c2966ec5101fb277 on Slack` onto a card), and drop an open-play line left dangling after the code is stripped out of it.
- **The tennis reservation index's "Reservation Courts" and "Walk-on Courts" OVERLAP — never sum them.** Riverside 119th's own page reads "Ten outdoor hard courts. Reservation Courts: 2" while the index lists 2 and 10. Adding them made the card say "2 of 24 courts reserved" beside a "20 courts" chip. Both halves of the occupancy build now take their denominator from the GIS count, matching what the card displays.
- **NYC outdoor pins close at real dusk, not a fixed hour.** A flat window is wrong for a city where dusk swings from ~4:30 PM in December to ~8:45 PM in June — it called courts open in winter darkness and closed on summer evenings. NYC Parks' own tennis page says courts run "8:00 a.m. to dusk", so the sourced 8 AM open stays and the close comes from the **`DUSK`** the permit API returns per date (captured by the same sweep, refreshed daily, mapped date→weekday in `data/cities/index.js`). Floodlit facilities run later **per sport**, from `LIGHTS` (the `ExtendedLightingFields` GeoJSON linked off the permit map — filename is content-hashed, so discover it, don't pin it): a park whose soccer pitch is lit until 11 PM says nothing about its unlit basketball court, and the expansion keeps them separate. Only facilities with a **published** lights-out get extended — ~85 pins carry Socrata's `field_lighted` flag but no end time, and those keep dusk, because understating hours sends someone home early while overstating them sends someone to a dark court. `PARK_HOURS` in the generated outdoor file is now only the fallback (a failed/stale build, or a city with no dusk source). `postbuild-web.js` says "8 AM to dusk daily" and names which sport has the lights.
- **nycgovparks.org's WAF answers a heavy caller with an empty 200, not an error.** The reservation build therefore does its ~7 HTML page loads **before** the 217-request sweep, and retries with long backoff; running them after got every page served an empty body. Back-to-back local runs still trip it — the cooldown outlasts the retries — which is exactly why the tennis half has its own cache fallback.
- **Sport & class filters self-hide by data presence**: amenity chips (`AMENITIES` in `App.js`) and class category chips only appear when some visible record qualifies, so NYC-only filters (clay/turf/full-court/water/permit; nature/philanthropy categories) never show for SF, and SF-only ones (nets/wall/golf) never show for NYC. **Adding a filter that reads a new data field just works this way** — no per-city conditionals needed.
- **The sport lists themselves are city-scoped too, through one helper**: `sportsInCourts(list, courts, keep)` in `lib/sports.js` counts a sport as present when some court in view carries drop-in hours for it, and every picker runs its own list through it — the map's sport dial (`MAP_SPORTS`), the interest pickers (`SPORTS`: onboarding + profile favorites, via a `sports` prop from `App.js`) and the three social composers (`RunModal`/`SignalModal` on `PLAN_SPORTS`, `SessionModal` on `SPORTS`, all derived from the city-filtered `courts` prop they already receive). So SF never offers handball and NYC never offers golf, and neither can open onto an empty court list; `App.js` also falls back to `DEFAULT_SPORT` when a city switch strands you on a sport the new city lacks. **`keep` is the part not to drop**: it forces ids in regardless, because hiding an *already-chosen* sport is a bug — a favorite saved in NYC must stay visible in SF or it can never be un-picked, and a signal's own sport must survive on the session sheet since signals arrive from other metros. The list falls back to the full one when the intersection is empty, so unloaded data can't render an empty picker.

**Adding another city:** one entry in `lib/cities.js` + a `scripts/cities/<id>.js` config on the Socrata adapter (config-only for another Socrata portal like Chicago) + an import line in `data/cities/index.js`. A non-Socrata portal (Seattle/LA ArcGIS) needs a new adapter module, dispatched by the config's `kind`.

GitHub Actions crons re-run the builds and commit only when the generated data changed: `refresh-schedules.yml` runs `build:data` weekly (SF courts/reservations/directory/classes/**pools** + all `build:nyc*`), `refresh-classes.yml` re-scrapes SF **and** NYC classes plus SF volunteer workparties every 6h (their "still needed" counts move like enrollments), `refresh-nyc-reservations.yml` re-sweeps NYC permits + tennis daily, and `refresh-reservations.yml` re-scrapes rec.us occupancy every 3h (bookings change hourly, so the weekly snapshot goes stale fast). On native the court card also fetches a **live** rec.us reading for the open location (`lib/reservationsLive.js`, mirrors `lib/classesLive.js`) and overlays it onto the snapshot's `reserved[sport]` — so "% booked at 3 PM" is real-time; web CORS-falls back to the snapshot and the card labels freshness ("Live from rec.us" vs "as of M/D"), only asserting a hard "🔴 Fully booked" when the reading is live or the snapshot is <6h old. **When adding a new generated file, also add it to the workflow's `FILES` commit list** or the refresh will run but never commit it. Because reservation/class/pool slots are date- or season-keyed and go stale, this refresh is what keeps "right now" accurate.

### 5. The assistant (`chatbot/` + `lib/assistant.js`)

An **optional, self-hosted** natural-language layer over the same data. It is a **separate Python/FastAPI process, not part of the app bundle**: the app talks to the service, the service talks to a model (Ollama or Anthropic), and that split exists so the provider key stays server-side and never reaches a phone. Gated on `EXPO_PUBLIC_ASSISTANT_URL` exactly the way `lib/supabase.js` is gated on its keys — unset (what production ships) means `enabled` is false and `AssistantHost` renders `null`. Full setup, provider notes and tool list: **`chatbot/README.md`**.

**The load-bearing rule: retrieval is deterministic Python, the model never decides a fact.** It picks a tool, fills its arguments, phrases the result — so it cannot decide whether a court is open and cannot invent an opening. Three corollaries that are easy to undo by accident: payloads are projected **narrow** (a court's ~3KB reserved-slots table shipped next to its hours buried them and produced "check the app for fees" *with the fees in context*); result keys are named for **the question they answer** (`percent_booked_at_asked_time`, not `percent_booked` — a well-named key outperforms a system-prompt rule, which a small model obeys inconsistently); and a never-recorded field returns an explicit `UNKNOWN` so absence can't read as "none".

**`npm run export:chatbot` is the only place that knows how a court is assembled.** It reproduces `lib/useCourts.js`'s merge and resolves each sport's week by calling the app's own `lib/hours.js` — which is why `resolveDropinWeek()` is *exported* from there. Never reimplement the open-play carve-out or `playWeek` precedence on the Python side; the two copies would drift on first change. Snapshots (`chatbot/data/*.json`) are gitignored and point-in-time — **re-run the export after any data refresh**, and on a fresh clone before first run.

**`AssistantHost` is mounted in `App.js` outside the tab switch, and that placement is the design.** It owns the conversation (`turns`), so the thread survives navigation; mounted inside a screen, the thread resets on every tab change — fine for a tab you sit in, unacceptable for a launcher that follows you. `AssistantThread` therefore takes `turns`/`onTurnsChange` from props (falling back to local state so it still works standalone) plus an `embedded` flag: filling a tab it must clear the floating `BottomNav` by hand (`insets.bottom + 96`, same as `ClassesScreen`), but inside the sheet there is no nav to clear and that padding leaves a dead band.

**On-screen context is passed as pointers, not facts.** `state.screen` / `court_id` / `court_name` / `sport` tell the service *which* record to look up — every hour and price still comes from a tool, and `_screen_phrase()` says so in the prompt ("being on screen is not knowing its hours") because the risk of handing a model a court name is that it starts answering from it. A name with **no id** is dropped entirely: it can't be looked up, so offering it invites exactly that. Like the timestamp, this rides the **last user turn, never the system prompt** — the system prompt is the cached prefix, and anything volatile up there re-bills it every question.

Gotchas worth not rediscovering:
- **Coordinate shape.** `App.js` stores a fix as `{ lat, lng }`; Expo's position objects use `{ latitude, longitude }`. `lib/assistant.js` accepts **both** — reading only the latter meant coordinates were never sent, and it failed *silently* because a missing origin just drops distance sorting.
- **The sheet needs all three device-only patterns** (all invisible on web): a **static numeric `maxHeight` in `StyleSheet.create`** (percent and inline/array numerics don't constrain under native Yoga), the backdrop as an **absoluteFill `Pressable` sibling behind the sheet** (a `Pressable` *ancestor* swallows the ScrollView's pan gesture and scroll silently dies), and **`zIndex` on the overlay wrapper**, not only on its children — a positioned `View` forms its own stacking context, so `60`/`61` inside it still lose to `App`'s `navWrap` (50) and the nav pill eats taps meant for the composer.
- **The fetch timeout is 90s** (`AbortController` — RN's fetch has none). A local 8B model takes 20–45s for a question needing a tool call, so a normal 10s would fail every request.
- **Offline behaviour is deliberate.** `lib/assistantFallback.js` answers questions *about the app* on-device (8 topics × 3 languages, amber "offline" bubble so they can't read as live) and **refuses live-data ones** — "how much does the pool cost today?" matches the pools topic on the word "pool", and answering it offline would dodge the question actually asked. Hours/prices need the service; saying so is the honest answer.
- **`assistant.*` i18n keys need en/zh/es parity** like everything else (`npm run check` enforces it).
- **`app.py`'s handlers are sync `def` on purpose** — `agent.answer()` blocks for seconds and FastAPI runs sync handlers in a worker thread. Wrapping blocking calls in `async def` would freeze the event loop process-wide on every question.
- **Spending controls are opt-in and default off** (`chatbot/limits.py` + the `ASSISTANT_*` vars): a shared bearer token, per-IP rate limits, and a **global daily budget**, which is the one that actually bounds the bill — per-IP limits are defeated by definition by a distributed caller. Off by default because requiring a token on localhost gets routed around; boot logs a warning in that posture. Limit state is **in-memory and per-process**, so the service is single-worker by design. `EXPO_PUBLIC_ASSISTANT_TOKEN` ships **inlined in the bundle and is not a secret** — it removes drive-by traffic, nothing more; the limits are the real guard.
- **Anthropic defaults to `claude-haiku-4-5`.** The reasoning is already done in Python — the model picks a tool and writes a sentence — so a frontier model is paying for work that isn't happening. This is the largest cost lever, ahead of the limits, because it lowers the cost of every legitimate request rather than capping how many are allowed.
- **Coordinates are transmitted but not *collected*, and that distinction is load-bearing.** `lib/assistant.js` posts `lat`/`lng`; `agent.py` turns them into an `origin` tuple for a haversine and drops them. They are never persisted, never logged, and **never sent to the model** (`origin` is keyword-only and absent from the tool schemas; results carry `miles_from_user`). That keeps the app inside Apple's "no longer than necessary to service the request in real time" exemption, so the privacy label's *Location: Not Collected* stays true with the assistant on. It is a convention, not a type — one `log.info("state=%s", state)` would falsify the App Store label silently — so it's **enforced by tests**: `TestCoordinatesStayInsideTheRequest` (`tests/test_agent.py`) and `TestRequestLogging` (`tests/test_app.py`). Break either on purpose and `docs/privacy-nutrition-label.md` tells you what else must change.
- **Users' questions, unlike their coordinates, do reach the model provider**, so enabling the assistant in a shipped build needs a policy disclosure. `npm run check` fails if an `eas.json` profile sets `EXPO_PUBLIC_ASSISTANT_URL` while `public/privacy.html` doesn't mention the assistant. It keys off `eas.json`, not the ambient env, so local assistant work doesn't trip it.

## Environment & config

All runtime config is `EXPO_PUBLIC_*` (inlined at build time, client-safe — the Supabase anon key is protected by RLS). Copy `.env.example` → `.env`. The app runs fully **signed-out with no env vars set** (bundled data + local check-ins); env vars progressively enable remote data and social features. Restart with `npx expo start -c` after changing `.env`.

`ANTHROPIC_API_KEY` is **not** an app var — it's used by `build:classes` / `build:nyc*` (CI/local) to translate class titles, and by the `chatbot/` service, which reads its own copy from `chatbot/.env` server-side. Never expose it to the web build; only the `EXPO_PUBLIC_*` vars belong in the host's env. `EXPO_PUBLIC_ASSISTANT_URL` is the assistant's on/off switch: unset in production, so the feature ships inert.

## Deploy (web)

**Vercel Analytics** is mounted web-only via `components/WebAnalytics.web.js` (renders `@vercel/analytics/react`), with a native no-op `WebAnalytics.js` — same `.web.js` platform-split as `CourtMap`, so the DOM-based lib never enters the native bundle. Use the `/react` entry, not `/next` (this is a react-native-web SPA). The launch splash is `expo-splash-screen` (config in `app.json` plugins → `assets/splash-icon.png`, the running stick figure). The app is **iPhone-only** (`ios.supportsTablet: false`) — runs on iPad in compatibility mode, no iPad assets needed.

**The install prompt** (`lib/getApp.web.js` + `components/GetAppPrompt.js`, native no-op `lib/getApp.js` — same platform split as `crash.js`/`WebAnalytics.js`) answers one question, "can this visitor install the app right now?", with two surfaces. **Desktop** — any browser, including desktop Safari — gets a corner **QR card**: it cannot install anything, so a Download button asks someone to remember a chore, while a code closes the loop with the phone already in their hand (`components/QRCode.js` renders it, no new dependency — friend invites already use it). A **phone** gets a slim dismissible bar floating in the gap above the nav pill, but **only on iOS browsers that are not Safari** (Chrome/Firefox/Edge/Opera/GSA), because `scripts/postbuild-web.js` already injects `<meta name="apple-itunes-app">` into `index.html` and every prerendered page — Safari renders Apple's own smart banner there, and a second ask would stack on it. **Android gets nothing**: `eas.json` is iOS-only, so an App Store link is a dead end. The split is by **device class, not viewport width** (a narrow desktop window still gets the QR, and a phone never gets a code to scan with the device holding it). Timing and frequency are the load-bearing half: never on first paint (both wait for a real interaction **and** a delay — 12 s bar, 45 s QR), one ask per session app-wide (`markGetAppAsked`, reserved so a future contextual sheet can claim the session rather than stack on this), and an **escalating dismissal ledger** in `recreate.getapp.v1` (7 days → 30 days → never), taking `lib/rateApp.js`'s stance that a prompt returning on the same terms after a dismissal is worse than one that never asked. `?from=app` retires it permanently; `?getapp=bar|qr` forces a surface for previewing (skips the device check, delay and snooze). The bar does **not** move the nav — `App.js` adds `GET_APP_BAR_H` to `navClearance`, so the recenter/Nearby buttons and the court card lift instead and the nav stays put. A full-screen interstitial is deliberately **not** on the menu: Google demotes intrusive mobile app interstitials, and the ~2,000 prerendered pages below *are* the acquisition channel.

The web target is a **static SPA export** (`npm run build:web` = `expo export --platform web` → `dist/`, then `scripts/postbuild-web.js`), served by Vercel (`vercel.json`: build command, `dist` output). Set the three `EXPO_PUBLIC_*` vars in the Vercel dashboard (a CI build has no local `.env`). **`vercel.json` deliberately has NO catch-all rewrite to `/index.html` — do not add one back.** The app routes entirely on query params (`lib/urlState.web.js`: `tab`/`sport`/`fav`/`court`/`add`/`city`), so it only ever loads at `/`; invite links are `/?add=<code>`, privacy and support are real files. A catch-all bought nothing and made every unknown path answer **200 with the app shell** — a soft 404, which Google flags and spends crawl budget on. It matters because ~800 generated URLs have entities that come and go (a rec center whose open-gym schedule empties out loses its page on the next scrape), and those indexed URLs must 404 honestly rather than resolve to a decoy. Unmatched paths now hit a generated `404.html` (noindex, no canonical, absent from the sitemap) that lists every sport and city index. **SEO (`scripts/postbuild-web.js`)**: the raw export is an empty JS shell Google can't index, so the postbuild pass injects real `<head>` metadata into `dist/index.html` and prerenders static landing pages from the bundled `data/` modules — with addresses, drop-in hours, JSON-LD, and links into the app via the URL-state params, plus `sitemap.xml`/`robots.txt`/`og.png`. Vercel serves these real files ahead of anything else, so they coexist with the app at `/`. **`og.png` is a purpose-built 1200×630 card rendered from `assets/og-card.html`** (regeneration command in that file's header), not the app icon — Open Graph wants 1.91:1 and every share surface center-cropped the square icon; the pages also declare `og:image:width/height` and `twitter:card: summary_large_image`, without which a wide image still renders as a small square thumbnail. The build **fails** if `assets/og.png` is missing rather than silently shipping pages with no share image. Page generation is **city-driven** (`CITY_CFG`): each city contributes one page per playable sport it has courts for, plus its class index; SF adds `/golf` and `/pools`. **SF paths are load-bearing** — `/basketball`, `/pools`, `/classes` … are already indexed, so SF alone has an empty path `prefix` and every other city is namespaced (`/nyc/basketball`). A sport with more than `SPLIT_OVER` courts in one city splits its outdoor list into subregion pages (`/nyc/basketball/queens`) — NYC has 620 basketball courts, which is not one readable page — and a subregion needs `SUBREGION_MIN` courts to earn a URL, with the remainder listed on the parent so no near-empty page ships. Each page's JSON-LD `ItemList` describes only what that page renders. Cities whose outdoor pins carry a **synthetic** park-hours window (`cfg.parkHours`, NYC) render facility facts (court count, lights, surface) instead of hours — printing "Mon–Sun 8 AM–8 PM" on 620 first-come courts is noise, not a schedule. Beneath the indexes sit the detail pages: one per **court** (`/court/<id>`, with the full weekly schedule, facility facts, reservation occupancy and nearest same-sport alternatives), **pool** (`/pools/hamilton`) and **golf course** (`/golf/lincoln-park`), plus multi-sport **area hubs** (`/sf/mission`, `/nyc/brooklyn`, gated at `AREA_MIN` courts and capped at `AREA_SPORT_CAP` per sport, handing off to the sport×subregion page for the rest). `earnsPage()` is the thin-content gate: real schedule data always qualifies, but a synthetic-hours outdoor pin must clear `NYC_MIN_COURTS` or offer 2+ sports — the ~320 that don't are still listed with the same facts on their borough page, and publishing them as stubs would risk the pages that do work. **Every generated page must have an inbound internal link** (sport pages carry the "Browse by area" block, court pages link their area hubs, the golf index links each course); a page reachable only from `sitemap.xml` gets crawled but reads as unimportant. Landing pages deep-link via **`?city=`** (`lib/urlState.web.js` → `App.js`), which is what makes a NYC page open the app on NYC rather than the stored/default metro; it counts as an explicit pick for the session (so a later location fix can't yank the visitor away) but is deliberately **not persisted** — otherwise one NYC link would strand an SF user on NYC forever. The site origin and the App Store id are hardcoded there (`SITE`, `APP_STORE_ID` — the id drives both the `apple-itunes-app` smart banner and the install CTAs) — update `SITE` if the domain changes, and keep `vercel.json`'s build command on `npm run build:web`. Note: the live ActiveNet class-availability fetch (`lib/classesLive.js`) is blocked by CORS on web and falls back to the bundled baseline — expected; native isn't bound by CORS.

## Deploy (native) — crash reporting & OTA updates

**Sentry** (`@sentry/react-native`) is native-only via `lib/crash.js` + a no-op `lib/crash.web.js` (same platform split as `WebAnalytics`), gated on `EXPO_PUBLIC_SENTRY_DSN` — unset means fully disabled, so dev and web are unaffected. `index.js` registers `withCrashReporting(Root)`; `metro.config.js` wraps Expo's default config with `getSentryExpoConfig` (harmless when disabled). Init is privacy-minimal: `tracesSampleRate: 0`, `sendDefaultPii: false`, and **never call `Sentry.setUser`** — crash data is declared "not linked to identity" in `app.json` `privacyManifests` + `docs/privacy-nutrition-label.md` + the privacy policy, and linking it would falsify all three. Sourcemap upload is wired via the `@sentry/react-native/expo` plugin in `app.json` (org `recreate-o6`, project `recreate`) and needs `SENTRY_AUTH_TOKEN` set as an EAS secret (builds without it still succeed — upload is skipped, stack traces just come back unsymbolicated).

**EAS Update (OTA)**: `app.json` sets `updates.url` + `runtimeVersion.policy: "fingerprint"`, and the `preview`/`production` build profiles in `eas.json` pin matching channels. Ship a JS-only fix with `npm run update:prod` (= `eas update --channel production`) — installed apps fetch it on next launch, no App Store review. The fingerprint policy means an update only reaches builds with identical native code, so **adding/upgrading any native module requires a new store build** (`eas build`) — the OTA update will silently not apply to older binaries. Both features touch native config, so the first build after enabling either must be a full rebuild (`npm run ios` locally or `eas build`).

**The App Store rating prompt (`lib/rateApp.js`)** rides on a crowd check-in and nowhere else — the user is at the court, has just reported how busy it is, and the app has visibly worked. iOS allows **3 prompts per user per year**, app-wide, and reports nothing back (no callback, no way to know whether the sheet appeared or whether they rated), so the only lever is *when* to ask and a wasted request is gone for months. Hence the gates: the user's **3rd** report or later (never a first-timer, who has no opinion yet), a ~4-month cooldown plus a per-session guard, and `isAvailableAsync()` so it never fires on web or in TestFlight. The cooldown is written **before** requesting, not after — the outcome is unobservable, and asking twice because a write failed is worse than skipping a cycle. It is fired from a `setTimeout` and never awaited, so it cannot delay or fail the check-in it rides on. Apple forbids screening users first, so there is **no "do you like the app?" pre-dialog** — ask or don't. `expo-store-review` is native, so this cannot ship over the air; it needs `eas build` and batches with the App Store Connect metadata (name/subtitle/keywords are version-level and only editable against a version in "Prepare for Submission").
